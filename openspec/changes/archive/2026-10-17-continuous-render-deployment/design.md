## Context

`deploy-pr-preview.yml` currently deploys the shared `goonbash-test` Render service only on `pull_request` events (opened, reopened, synchronize). Merges to `main` do not trigger any deployment, so after a PR merges, the test environment still shows the last PR's commit (or an even older one) until another PR happens to be opened. There is also no visible indicator of which commit is actually running, so testers cannot verify freshness. This change makes "the latest pushed commit, from any source, is always what's live" and surfaces that fact in the UI.

## Goals / Non-Goals

**Goals:**
- Trigger the same Render deployment on both `pull_request` events and `push` events to `main`.
- Ensure whichever commit was pushed most recently (PR branch or `main`) is what ends up live, without manual intervention.
- Propagate commit SHA + deploy timestamp to the running app so it can be displayed.
- Expose that info via a minimal backend endpoint and a small, unobtrusive frontend badge/overlay.

**Non-Goals:**
- Per-PR isolated preview environments (still a single shared service, per the existing design decision).
- Production environment / separate prod Render service (out of scope; this only affects the shared test service).
- Historical deployment log/dashboard (only "currently live" commit is shown, not history).

## Decisions

**1. Workflow trigger: add `push` on `main`**
- Add a `push` trigger scoped to `branches: [main]` alongside the existing `pull_request` trigger in the same workflow file.
- Rationale: Single workflow keeps deploy logic (API call, polling, commenting) in one place; avoids duplicating the Render API call logic in a second workflow file.
- Alternative: Separate `deploy-main.yml` workflow (rejected — duplicates ~80 lines of deploy/poll logic; harder to keep in sync).

**2. Race condition / "latest wins" ordering**
- Rely on Render's own deploy queueing: each triggered deploy uses the commit SHA checked out in that workflow run's context (`github.sha` for push, `github.event.pull_request.head.sha` for PR). If two workflow runs overlap, whichever Render deploy finishes last is what's live — matching "always the latest pushed commit" semantics well enough for a shared best-effort test environment (already an accepted trade-off per the parent deployment design).
- Rationale: Render already serializes deploys per service; no need for custom locking given the existing "shared environment, last write wins" model.
- Alternative: Add a GitHub Actions concurrency group keyed on the service to cancel superseded runs (`concurrency: { group: render-test-deploy, cancel-in-progress: true }`). **Adopted as an additional safeguard** so an in-flight older deploy doesn't finish after a newer one and clobber it.

**3. Passing commit metadata into the deployed app**
- Use Render's deploy API `envVars` override (or, if unsupported for ad-hoc per-deploy overrides, update the service's env vars via `PATCH /v1/services/{id}/env-vars` immediately before triggering the deploy) to set `COMMIT_SHA`, `COMMIT_SHORT_SHA`, `SOURCE_BRANCH`, and `DEPLOYED_AT` (ISO 8601, generated by the workflow at trigger time).
- Backend reads these from `process.env` at startup and exposes them via `GET /deployment-info` returning `{ commitSha, commitShortSha, branch, deployedAt }`.
- Rationale: No need for a database or file-based state; env vars are simple, already how Render exposes config, and require no extra infrastructure.
- Alternative: Write a `deployment-info.json` file at build time via a build-command wrapper (rejected — more moving parts than env vars, and Render env vars are already the established pattern in this repo per `RENDER_SETUP.md`).

**4. Frontend display**
- Add a small fixed-position badge (bottom corner) rendered outside the Phaser canvas, populated by fetching `GET /deployment-info` from the backend once on load.
- Shows short SHA and a human-readable timestamp (e.g. `abc1234 · 2026-09-12 20:04 UTC`).
- Rationale: Minimal, non-intrusive, doesn't require changes inside Phaser scenes; easy to remove/hide later if desired.
- Alternative: Show it inside the game's lobby UI only (rejected — badge should be visible immediately, even before a lobby loads, to confirm the environment before any interaction).

**5. PR comment wording**
- Update the PR comment templates to note that the shared test environment now also updates automatically on merges to `main`, so a stale comment on an old, unmerged PR doesn't mislead reviewers into thinking their PR is still live after another PR/merge has superseded it.

## Risks / Trade-offs

**[Risk]** Two deploys (PR update + main merge) racing could still show a brief moment of the "wrong" commit if Render finishes them out of trigger order.
→ **Mitigation**: GitHub Actions `concurrency` cancel-in-progress per workflow reduces this; residual risk accepted as consistent with the existing shared-environment trade-off.

**[Risk]** Render API may not support per-deploy env var overrides atomically with the deploy trigger, requiring a separate PATCH call before deploying.
→ **Mitigation**: Design allows for a two-step call (update env vars, then trigger deploy); document actual API behavior during implementation (see Open Questions).

**[Trade-off]** The commit badge adds a small always-on network request and DOM element to the test build; acceptable since this is a test-only environment, not production-critical UX.

## Migration Plan

1. Add `push: branches: [main]` trigger and a `concurrency` block to `deploy-pr-preview.yml` (or rename it to reflect it now also handles main deploys, e.g. `deploy-render-test.yml`).
2. Extend the deploy step to compute `DEPLOYED_AT` and set/patch Render env vars before/alongside triggering the deploy.
3. Add `GET /deployment-info` endpoint to the backend reading the new env vars (with sensible local-dev fallbacks like `"local"` / `"unknown"`).
4. Add the frontend badge that fetches and renders this info on load.
5. Update PR comment copy to mention main-branch redeploys.
6. Manually verify: open a PR (badge updates), merge it (badge updates again to main's commit), push an unrelated commit to `main` (badge updates again).

## Open Questions

- Does the Render API support setting env vars as part of the deploy trigger call, or does it require a separate `PATCH` to the service's env vars beforehand? Needs confirming against Render's API docs during implementation.
- Should the workflow file be renamed (e.g. to `deploy-render-test.yml`) to reflect it's no longer PR-only, or kept as-is to minimize diff/history churn?
